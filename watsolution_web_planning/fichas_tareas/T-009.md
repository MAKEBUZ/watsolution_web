# [T-009] Asignar referencia Bold de forma atómica

- **Hallazgos que resuelve:** WS-005. Resuelve la parte descrita; el hallazgo completo exige todas sus tareas de corrección en la matriz.
- **Prioridad / Fase / Esfuerzo:** P0 / F1 Contención inmediata / 12–20 h-persona. Estado: Pendiente. Responsable sugerido: Backend / líder técnico, nombre por asignar.
- **Contexto y riesgo si no se corrige:** Dos aperturas simultáneas pueden perder la referencia de un pago. Dos solicitudes leen boldOrderId vacío y generan referencias distintas. La última actualización gana; un webhook de la primera referencia ya no encuentra factura y retorna sin conciliar (líneas 60–61), aun cuando el cliente haya pagado.

- Evidencia: WS-005: server/src/service/bold.service.ts:36.
- Cambio previsto o referencia operativa: server/src/service/bold.service.ts.
- Cambio previsto o referencia operativa: server/src/service/bold.service.spec.ts.

Los archivos bajo reportes se citan solo como evidencia y nunca son destino de implementación. Las rutas marcadas nuevas no existen todavía. Las líneas son del estado revisado y se ubican de nuevo antes de implementar.

- **Pasos de implementación (numerados):**

1. Bloquear fila dentro de transacción al crear/reutilizar boldOrderId.
2. Leer estado e importe bajo el mismo bloqueo; generar hash tras fijar referencia.
3. Probar doble clic, solicitudes simultáneas y factura ya pagada.

Esquema orientativo; no es un parche aplicado. Nombres nuevos requieren implementación y pruebas.
